# 0028 — Use Western `0–9` digits across customer-facing storefront numerals

Date: 2026-09-01

Status: accepted; storefront implementation verified in draft, native Arabic checkout blocked

## Context

The owner requires every number generated by the Calapres storefront to use Western digits,
regardless of whether the shopper selects Arabic or English. The previous theme intentionally
converted prices, quantities, cart counts, and other values to Arabic-Indic digits, while some
static sections used those digits directly. Late content from storefront applications could also
reintroduce a different decimal numeral system after the page first rendered.

The rule concerns store-authored numbers such as money, quantities, durations, dates, years,
result counts, and numbered interface values. It must not silently alter exact data entered by a
customer, an identifier, a URL, or machine-readable structured data.

## Decision

1. Render every store-authored decimal numeral with the Western glyphs `0–9` in every storefront
   locale. This includes prices, savings, quantities, cart badges, dates, years, durations, search
   counts, FAQ numbering, static editorial values, accessibility labels, and later theme-DOM
   content.
2. Normalize every Unicode decimal-number script to `0–9`, rather than limiting the rule to Arabic-
   Indic and Persian digits. Keep a comma as the storefront thousands separator and do not change
   currency, amount, price, rounding, or calculation semantics.
3. Keep the server-rendered source Western by removing the legacy Arabic-digit conversion and by
   replacing static non-Western digits. Use a guarded client-side normalizer only as a safety net
   for localized or application-injected visible content.
4. Never rewrite links, source URLs, element identifiers, field names, submitted field values,
   data attributes, scripts, JSON-LD, or other machine-readable values. Preserve exact customer-
   authored content, including engraving text, names, addresses, search terms, rich-text editor
   input, and gift-card codes, even when the customer deliberately types non-Western digits.
5. Direct native numeric controls to the English numeral presentation without changing their
   numeric value or validation behavior.
6. The theme guarantee applies to the Shopify theme-controlled storefront and password layout.
   Native Shopify checkout, externally hosted customer-account pages, cross-origin frames, and
   closed shadow roots are separate rendering surfaces that must be checked independently and must
   not be claimed as theme-controlled.

## Validation gate

Before production publication:

- validate JavaScript syntax, template JSON, section schema JSON, and the complete theme;
- prove conversion for Arabic-Indic, Persian, Devanagari, Bengali, Thai, full-width, and
  supplementary-plane mathematical decimal digits;
- prove that customer-authored content and machine-readable attributes remain unchanged;
- test initial and dynamically inserted content, product prices, the cart badge, cart quantities,
  totals, dates or years where present, and mobile layout in a real browser;
- inspect native checkout separately and record exactly what is and is not controlled.

## Verified draft record

Canonical GitHub `main` commit `f49f3871c4c650936925a0b55175ff17f29b245a` implements this rule in
the seventeen theme files that render prices, cart values, static numbers, customer-data boundaries,
and shared layouts. Shopify draft `165804638464`, `Preview — Western digits 0-9 2026-09-01`, is an
isolated duplicate of live theme `165777604864`; every uploaded file matches canonical source by
MD5 and size. The live theme was not changed.

Theme Check inspected 181 files with zero errors and the six existing remote-font warnings. The
independent suite converted all 680 Unicode decimal-number characters and passed syntax, dynamic-
DOM, customer-data, attribute-safety, and batching-performance checks. Browser verification passed
the homepage, product, cart drawer, standalone cart, About, and 404 surfaces, including a dynamic
quantity and total update and a 390 px no-overflow check. A customer-entered search term `١٢` stayed
exact while the store-generated result count used `0`.

The native Arabic checkout remains outside this decision's executed coverage. It displayed
`١ عنصر` and `٣٩٠٫٠٠ ر.س.`, and a direct `ar-SA-u-nu-latn` locale test did not change those values.
The Admin API confirms the store is on Basic. Shopify's current platform documentation states that
theme custom CSS does not apply to checkout and information, shipping, and payment-page UI
extensions require Plus. No documented Basic control can replace Shopify's native checkout-number
formatting. Publication therefore requires an explicit owner decision: accept the native Arabic-
checkout exception while publishing the storefront improvement, or use an English checkout whose
native numbers are Western. Neither choice has been executed.

## Rollback

Restore only the files named in the production record from the parent of the eventual implementation
commit, then recheck a product, search, cart, customer-data boundary, and checkout. Do not change
prices, inventory, products, orders, payments, shipping, taxes, or customer data during rollback.
